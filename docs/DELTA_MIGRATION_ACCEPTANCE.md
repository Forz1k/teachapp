# Delta LAB — чек-лист перехода (не production)
 
**Текущий рабочий протокол TeachApp 5.1.1 не меняется.** Это техническая репетиция переноса, а не инструкция для самостоятельного изменения рабочих адресов.
 
## До копирования
- [ ] Отдельные локальные серверы, синтетические записи, разные ключи и пароли.
- [ ] Проверена полная защищённая копия каждого исходного устройства; сохранены пароли и текущий исходный адрес.
- [ ] Все устройства синхронизированы; inspectDeltaMigrationDevice показывает clean-source для каждой действующей копии. Не считать fresh-device готовым к переносу.
- [ ] Нет черновиков LIVE в контуре тренера. Согласованы удаления и конфликты.
- [ ] LAB Node relay: отдельный ключ барьера по контуру, проверенный файл и явное подтверждение блокировки точной ревизии. Production Cloudflare/v2 пока не поддерживает барьер; ручное подтверждение не эквивалентно серверной блокировке.
 
## Репетиция
- [ ] prepareDeltaMigration: источник читается, целевой контур пуст, в файл записаны два зашифрованных снимка.
- [ ] Сохранить файл отдельно, открыть через openDeltaMigration, проверить контур, ревизию, workspace ID, digest и совпадение содержимого.
- [ ] commitDeltaMigration только после подтверждения. Проверить verified-copy, а не source-changed, independently read/verify destination. Новый workspace ID, ревизия 1, старый сервер неизменен.
- [ ] При наличии `sourceFenceToken` и `sourceFenceId` ожидается `verified-fenced-copy`: серверная блокировка проверена до/после копирования, запись источника запрещена HTTP 423; это ещё не разрешение переключения устройств.
- [ ] Повтор операции не создаёт новую ревизию. Попытка другого снимка в непустой контур запрещена.
- [ ] Проверить прерывание, перезапуск, устройство с локальными изменениями, позднюю запись источника, изоляцию контуров, восстановление файлов.
 
## Блокеры рабочего перехода
- [ ] Production изоляция, серверный барьер записи, долговременная авторизация и защита от злоупотреблений.
- [ ] Безопасная привязка проверенной локальной базы к новой последовательности, совместимость старых версий, атомарное переключение профиля и контрольных точек на каждом устройстве.
- [ ] Реальные ПК и iPhone: офлайн, переподключение, резервирование, отзыв ключей и откат.
- [ ] Решение об отключении старого сервера только после независимой приёмки. Не удалять его данные автоматически.
 
При source-changed не переключать устройства: целевая копия может быть устаревшей. Не очищать IndexedDB и не заменять локальные данные резервной копией вслепую.

## Барьер Node LAB (кандидат этапа 6)

Только явная конфигурация конструктора `createRelay({migrationFenceTokens:{coach: отдельный_ключ}, ...})` с HTTP loopback origin; обычный CLI и production Worker не меняются. `GET/PUT /v1/migration-fence/{area}` используют отдельную привилегию. Блокировка точной непустой ревизии и снимок хранятся в одном атомарно заменяемом файле, обычное чтение остаётся совместимым, запись запрещается даже после перезапуска без конфигурации привилегии. Повтор того же ID/ревизии безопасен. Автоматического снятия барьера нет: безопасный rollback и локальный cutover остаются отдельными этапами. Не использовать реальные данные; старый бинарник не знает о барьере, поэтому не откатывать серверный код на него.

## Локальное переключение устройства (кандидат этапа 7)

ID барьера равен `migrationId` из проверенного файла (`destination workspaceId`): не использовать случайный ID от другого плана. Обычный токен исходного контура может только читать `GET /v1/migration-fence-status/{area}`; административный ключ устройству не передаётся. `cutoverDeltaMigrationDevice` в Node LAB проверяет старую контрольную точку, локальные данные, зафиксированный источник и точный целевой якорь ревизии 1. Preview не меняет БД. При подтверждении с ID и исходной ревизией контрольная точка и локальная LAB-привязка записываются в одну транзакцию IndexedDB; повтор не переписывает данные. Пароли и ключи остаются в проверенных зашифрованных файлах, обычный TAP1/TAD2 профиль не переключается. Изменение локальной записи во время сетевой проверки прерывает переход. После локального переключения используется только явно созданный LAB-адаптер; обычный старый клиент обнаружит другой endpoint и остановится. Не выполнять запись назначения до переключения всех устройств. Нет распределённой транзакции между серверами, production-профиль, серверный барьер назначения и проверка rollback остаются отдельной задачей. Не применять к пользовательским данным.

## Безопасный откат до первой записи назначения (этап 8, LAB)

1. Проверить защищённые копии всех устройств. Не применять к действующему серверу. Откат возможен только на исходной ревизии назначения 1, до любых delta/compact/rotate. `sealDeltaMigrationRollback` проверяет файл и исходный барьер, затем отдельным ключом `TEACHAPP_DELTA_SEAL_HASHES` необратимо закрывает назначение. SQLite-транзакция запрещает все записи, включая multipart и повторы; чтение остаётся доступным. Повтор того же ID безопасен.
2. На каждом переключённом устройстве `rollbackDeltaMigrationDevice`: сначала preview, затем явное подтверждение точного ID и исходной ревизии. Только совпадающие данные и контрольная точка; несогласованные изменения запрещают автоматический возврат. Одна транзакция возвращает исходную контрольную точку, снимает LAB-привязку и удаляет устаревший статус. Записи пользователя не заменяются.
3. Владелец подтверждает возврат **всех** устройств. `resumeSource` доступен только с отдельным ключом исходного барьера и предварительно заданным `migrationRollbackTargets` (проверенный loopback endpoint и отдельный токен чтения). Сам Node relay читает необратимый статус назначения, проверяет ID и ревизию, затем атомарно снимает исходный барьер и сохраняет отметку rollback. Клиентское обещание без серверного подтверждения недостаточно. Повтор не открывает другой контур. После возврата новый перенос в эту тестовую папку запрещён; использовать новую изолированную репетицию.
4. Если назначение уже изменилось, кто-либо не проверил офлайн-устройство или есть локальные правки, **не разблокировать источник**: сохранить копии, выполнить отдельное согласование данных. Нет автоматического возврата после ревизии 1 и нет восстановления старых бинарников. Проверка возврата каждого физического устройства и production миграция остаются отдельными условиями.

## Cloudflare source LAB (этап 9, кандидат)

`wrangler.migration-source-dev.jsonc` — отдельное имя, отдельное хранилище, без workers.dev и preview URLs. Только локальная репетиция с явным `TEACHAPP_SYNC_MIGRATION_SYNTHETIC=true` и отдельными `TEACHAPP_SYNC_FENCE_HASHES`; обычный `wrangler.jsonc` не меняется. `/v1/migration-fence/{area}` — привилегированная фиксация точной ревизии. `/v1/migration-fence-status/{area}` и `/v2/migration-fence-status/{area}` — чтение соответствующим действующим ключом. Обе версии PUT используют один SQLite Durable Object и проверяют барьер в транзакции; старые клиенты получают 423. Уже установленный барьер сохраняется при отключении LAB-маршрутов. Сохранённые и отозванные ключи устройств не могут стать ключами барьера; регистрация зарезервированного ключа запрещена.

Синтетический перенос и атомарное переключение/локальный возврат поддерживают `protocolVersion:2`; LAB-привязка фиксирует версию источника. В первом варианте этапа 9 снятие барьера отсутствовало; ниже описана реализованная подписанная квитанция безопасного снятия в LAB. Без закреплённого проверочного ключа и commitment источник остаётся read-only. Требуются миграция обычного профиля устройства, физическая приёмка и отдельное разрешение на рабочее развёртывание. Не устанавливать барьеры на действующем сервере.

## Подписанная квитанция отката Cloudflare (LAB)

Для отдельного контура заранее создать независимую пару ECDSA P-256. Закрытый JWK `TEACHAPP_DELTA_ROLLBACK_SIGN_KEYS` остаётся только у тестового Delta Worker; публичный JWK `TEACHAPP_SYNC_ROLLBACK_VERIFY_KEYS` закрепляется у тестового источника. Не использовать один ключ в обоих контурах. При freeze требуется `destinationAnchorCommitment` из проверенного плана (SHA-256 от одиночного зашифрованного снимка либо ID проверенного multipart-манифеста); источник атомарно фиксирует его вместе с публичным ключом и ревизией. `rollback-receipt` выдаёт подпись только после необратимого seal на ревизии 1. Подписываются версия, контур, UUID переноса, ревизия и commitment. Клиент не может указать собственный проверочный ключ. `resumeCloudflareSource` требует отдельный ключ исходного барьера, подтверждение защищённых копий и возврата всех устройств, а источник проверяет подписанную квитанцию с закреплённым ключом и точным commitment. Повтор безопасен; другой перенос в эту LAB-папку запрещён. При отсутствии ключа/commitment, изменённой подписи, другом контуре или другом снимке источник остаётся read-only. Обычная production-конфигурация и профиль не переключаются; физическая приёмка, защита серверных ключей и эксплуатационное развёртывание отдельно.

## Защита основного приложения при экспериментальной привязке (этап 10)

Маркер `sync-checkpoint-migration-{area}` не является профилем подключения. Если он присутствует, обычный автообмен и ручной обмен запрещены до обращения к явному LAB-адаптеру или согласованного возврата. Нельзя отключить контур с удалением checkpoint, нельзя восстановить полную копию поверх незавершённого переноса; проверка внутри транзакции. Предпросмотр сравнивает привязку, запись повторно проверяет её после шифрования и в транзакции. Независимый контур продолжает работать. Локальный статус не раскрывает ключи, пароли, адреса и ciphertext. Старый бинарник или восстановление хранилища сервера до seal не имеют этих гарантий: не откатывать код/серверную БД без отдельного согласования, не использовать старую signing identity после восстановления pre-seal копии.

Кандидат статического выпуска: [RELEASE-5.2-ACCEPTANCE.md](RELEASE-5.2-ACCEPTANCE.md). Номер кандидата не означает включение нового протокола в production.

## RC4 — HTTPS v3 candidate, ещё не production

Источник: отдельно разрешить `TEACHAPP_SYNC_MIGRATION_CANDIDATE=true`, точный `TEACHAPP_SYNC_MIGRATION_ENDPOINT`, per-area fence hashes и закреплённые публичные ключи квитанций. Не совмещать с LAB. Назначение: отдельный v3 Worker, per-area seal hash и signing key; до блокировки источника подготовить файл `prepareDeltaMigration({...args,candidate:true})`, сохранить и повторно открыть, сверить все устройства. Затем задать `TEACHAPP_DELTA_MIGRATION_GATES` для контура: {migrationId,anchorCommitment:destinationAnchorCommitment}. Сервер сохраняет gate в SQLite, удаление/изменение конфигурации не открывает запись. Только точный якорь файла допустим до активации, append/compact/rotate блокируются. Для этого режима подписанная квитанция обязательна. `freezeDeltaCandidateSource` проверяет пустое назначение и файл до блокировки; `commitDeltaMigration` проверяет действующий барьер и gate до/после копирования. На каждом защищённом v11 устройстве — экран «Перенос / возврат Delta v3», preview, копия, подтверждение ID/ревизии. Маркер и checkpoint фиксируются атомарно, обычный обмен закрыт. После подтверждения всех устройств оператор вызывает `activateDeltaCandidateMigration` с отдельным seal/activation token; затем каждое устройство выполняет finalize. Не выполнять компактизацию до finalize всех устройств. До активации возможен seal с `sealDeltaMigrationRollback`, возврат каждого устройства и подписанная квитанция для `resumeCloudflareSource`; после активации автоматический rollback запрещён даже без append. Утраченная/несогласованная ревизия требует отдельного согласования. Ручное подтверждение всех устройств не заменяет инвентаризацию, физический акт и независимый аудит. Никаких реальных конфигураций/секретов в репозитории, не развёрнуто.

Для каждой изменяющей локальное состояние команды (cutover/finalize/rollback) требуется отдельный актуальный файл независимой копии v11 и пароль, отличный от паролей переноса. Копия дешифруется и сравнивается со всеми записями до CAS; любое изменение всей базы прерывает операцию. Preview остаётся read-only.
