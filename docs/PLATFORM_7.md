# TeachApp Platform — архитектура 7.0 (не production)
 
Личный офлайн-режим остаётся основным. Сервер 1.2 даёт индивидуальные ключи устройства только для двух целых контуров; он не является многопользовательской системой. Не выдавать ключ снимка спортсменкам и помощникам.

## Разделение данных
- Workspace: идентификатор владельца, участники, серверная авторизация, отзыв приглашений, отдельные ключи.
- School: школа/классы, доступ только назначенным учителям; никакой публикации здоровья.
- Team: команды, отдельные права тренеров и помощников, назначение активного матча.
- Athlete: минимальная отдельная проекция расписания, целей, заданий; только собственный идентификатор.
- Tournament: доступ назначенного организатора; публичный снимок отдельно от заявок.
- Public: только явный белый список полей, никаких private snapshots.

## Серверная граница
Модуль `server/workspace-policy.mjs` — проверяемый прототип политики, не подключён к действующему Worker. Сервер обязан определять actor из проверенной сессии, membership и resource из своей БД, а не из запроса клиента. Авторизация, проверка отзыва, idempotency key, CAS матча и запись события в одной транзакции. Нельзя отдавать клиенту полный снимок и скрывать лишнее средствами CSS. Проекции определяются на сервере. Лимиты и аудит по workspace, пользователю, IP; журнал без секретов и медицинских данных.

## До запуска
Только синтетические тестовые данные. Нужны безопасная регистрация, восстановление владельца, проверка серверных токенов, изоляция workspaces, хранение ключей, тесты IDOR и гонок, резервирование, согласие на обработку данных несовершеннолетних и процедура удаления. Не подключены кабинеты спортсменки и помощника, нет production API ролей. Реакции и голосования откладываются до проверенной защиты от накрутки. Не изменять рабочий Firebase/Cloudflare без разрешения. 

## Изолированный серверный кандидат

`server/platform-worker.mjs`, `server/platform-api.mjs`, отдельный `wrangler.platform-dev.jsonc` (workers_dev=false, маршрутов нет, включение только явным synthetic-конфигом). Это отдельный сервер, не текущий Worker/Firebase. Сервер разрешает bootstrap только по отдельному хешу root-ключа, выдаёт независимые bearer-сессии (7 дней), хранит только хеши, приглашения одноразовые 10 минут. Внутри отдельного Durable Object на workspace авторизация, запись, аудит и CAS выполняются синхронной транзакцией. Роли: владелец, тренер конкретной команды, помощник конкретного активного матча, спортсменка только собственного профиля. Школьный сервер и организатор пока не подключены. Роль и scope вычисляет сервер. Проекции ограничены составом, целями, заданиями, расписанием, ответом и счётом; медицинские данные и private backup не принимаются. Сессия владельца не продлевается; полноценное восстановление владельца ещё требуется. Серверная аренда LIVE на 45 с, поколение fencing, CAS ревизии и idempotency; отзыв освобождает аренду. Пока только базовый счёт/партии, не полный локальный протокол. Никакой связи с текущей публикацией Firebase, это не замена ей. Состояние ограничено 512 КБ, аудит 200 записей (не юридический архив). Перед production необходимы безопасная регистрация/восстановление, rate limits, долговременный аудит, резервирование/удаление, полный регламент, реальные устройства и отдельное разрешение.

## Тестовые кабинеты (localhost)

`platform-dev/index.html` — отдельная страница LAB, блокируется вне loopback; токен только в памяти, не хранится в URL/браузерной базе. Серверное ограничение CORS допускает точно заданный HTTP localhost для локального теста. Владелец создаёт синтетические команды и матчи, выдаёт приглашения, отзывает доступ и смотрит ограниченный аудит. Тренер получает свой состав и редактирует минимальный профиль спортсменки с CAS ревизии, помощник ведёт назначенный матч, спортсменка видит только личные цели/расписание/задания и отвечает фиксированными статусами. Публичное приложение и зрительский портал не связаны с LAB. Синтетические формы профиля пока используют JSON, production UX и регистрация требуют доработки. Для запуска локально: `python -m http.server 8099 --bind 127.0.0.1`, отдельный `wrangler dev --config wrangler.platform-dev.jsonc --local` с тестовым root hash, origin `http://127.0.0.1:8099` и явным synthetic=true. Не вводить реальные данные. CI использует динамический локальный порт и независимый временный storage.

## Восстановление владельца (LAB)

Владелец генерирует случайный 256-битный код в браузере и сохраняет его отдельно **до** подтверждения. Сервер хранит SHA-256 и версию, не сам код. `POST owner/recovery` доступен только владельцу и использует CAS версии. `POST recover` использует код строго в одном workspace, выдаёт новую сессию, отзывает прежние owner-сессии, отменяет их неиспользованные приглашения и освобождает их LIVE-аренды. Сохранённые матчи, составы и остальные действующие участники остаются; после восстановления необходимо проверить их список. Код можно использовать повторно при потерянном ответе, его смена отзывает старый. Нет восстановления по общему bootstrap root. Это репетиция, не production identity: остаются rate limits, защищённое хранение и резервирование, проверка реального устройства и эксплуатационная модель.

## LAB — ограничения запросов и жизненный цикл сессий

В Durable Object добавлены персистентные минутные корзины известных участников: чтение 240, изменения 180, операции доступа 24, восстановление 6, активация приглашений 64 на workspace. Ответ 429 с Retry-After, без автоматической повторной отправки. Недействительные произвольные токены не создают корзин и не расходуют лимит участника. Это не внешний IP/edge rate limiting и не защита от DDoS. Добровольный серверный отзыв собственной сессии освобождает LIVE-аренду, владелец должен предварительно иметь код восстановления. Владелец может явно удалить только отозванные/истёкшие сессии, без удаления матчей/профилей/аудита. Исправлен контроль размера состояния при активации приглашения. Production не включён.


## LAB — изоляция при создании матча и закрытие приглашений

Сервер сначала проверяет право team.write на идентификатор команды, затем существование команды. Для спортсмена, помощника и тренера чужой команды запросы к чужому и несуществующему ресурсу дают одинаковый 403; владелец сохраняет диагностический 404. При подтверждённом завершении матча одновременно удаляются приглашения помощников именно этого матча; незавершённая/отклонённая операция не меняет приглашения, другие матчи не затрагиваются. Уже активные помощники теряют доступ к завершённому матчу по существующей политике, их сессии не удаляются автоматически. Синтетические регрессии проверяют оба случая. Production и внешняя авторизация не меняются.


## LAB — барьер случайного публичного запуска

Конфигурация синтетического Worker принимает только точный loopback HTTP(S) origin и запросы с loopback URL; внешний origin, публичный hostname, неверный synthetic-флаг или root hash отключают сервис (503) до обращения к Durable Object. CI проверяет варианты URL и запуск реального локального workerd с внешним origin. Это дополнительная защита от ошибки конфигурации, не сетевой firewall: локальный запуск с --local --ip 127.0.0.1 и отсутствие production routes по-прежнему обязательны. Не использовать как production identity.

## LAB — очистка кабинета при приостановке страницы

pagehide и freeze закрывают текущий и незавершённый клиент входа, очищают форму и кабинет, прекращают обновление LIVE. Вход использует снимок адреса и workspace, секрет удаляется из поля до сетевого запроса. Ответ предыдущего входа и асинхронный расчёт recovery hash не могут продолжить работу в другой сессии. Это локальное закрытие: серверная сессия не отзывается, уже принятая операция не отменяется, аренда истекает по серверному сроку. Реальный Chromium smoke имитирует pagehide после входа и во время задержанного запроса. Не обещает стирание памяти браузера или проверку физического BFCache.

## LAB — управление подпиской из кабинета

Владелец, тренер и спортсмен могут проверить состояние, включить или отключить тестовую подписку своей сессии. Кнопки зависят от загруженной ревизии; при конфликте или неизвестном результате требуется повторно загрузить состояние, автоматической повторной записи нет. Endpoint генерируется исключительно в зарезервированном example.invalid, не отображается и не сохраняется клиентом. Разрешение браузера, PushManager и реальная доставка не используются. Chromium smoke проверяет включение и выключение из мобильного кабинета спортсмена на реальном локальном Worker, независимость состояния владельца и последующие API проверки.

## Входящие сигналы в кабинете спортсмена (LAB)

Отдельный блок позволяет вручную проверить общий сигнал и подтвердить просмотр. Не показывает данные задания, endpoint или произвольный серверный текст, не меняет ответы на задания. При конфликте ревизии/последовательности состояние сбрасывается, нужен новый GET. Ответ после смены сессии не отображается. Chromium smoke проверяет новый сигнал, конфликт после повторного изменения профиля, повторное чтение, подтверждение и последующее выключение подписки. Фоновая доставка и автоматическое подтверждение отсутствуют.

## RC6 preparation — atomic session credential rotation (LAB)

Authenticated `POST session/rotate` takes an empty JSON object. The server generates a fresh bearer secret and returns it once; the previous hash becomes invalid in the same workspace transaction. The member ID, role, scope, and absolute expiry do not change. Rotation is classified as an access operation, not a new rate budget. Any pending invitations issued by the rotating member are cancelled, LIVE leases are released with a new fencing generation, and enabled or previously configured synthetic notification subscriptions are disabled with a new revision. Scores and previously committed operations are retained. The owner must have an independent recovery code configured before rotation. A lost response is not automatically retried: the owner uses recovery; other members request a new invitation and the owner revokes the lost session. This API does not prove possession of a second factor, does not undo actions already committed using a compromised token, and is not a production identity provider. Browser controls and real push remain open. Only synthetic loopback data; no production routes, deployment, migrations or version bump.
