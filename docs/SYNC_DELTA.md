# Incremental sync — isolated candidate, not production

The current v1/v2 relays and automatic synchronization remain unchanged. This checkpoint adds a client-side delta codec and an explicitly labelled comparison in the manual preview. It does not send delta packets to the existing endpoints.

- A delta contains only per-store upserts and deleted IDs, with exact area, workspace, base and next revision, schema version, SHA-256 digests of canonical base/result, and the existing authenticated encryption envelope.
- Replay requires a verified base and a contiguous chain; it rejects unknown stores, duplicate or missing deletions, wrong scope, malformed records, incorrect digests, invalid relationships and wrong passwords. It never writes IndexedDB. A caller must supply a current full database to validate reconstructed scope and preserve other areas.
- The displayed estimate compares encrypted PUT sizes, including UTF-8, GCM tag and base64; the current full snapshot is still the actual payload.
- SHA-256 digests are encrypted inside each packet. They are not server-side authorization. A future isolated relay needs scoped credentials, CAS, bounded storage/paging, a durable full anchor, compaction and a safe initial download, then real multi-device and rollback tests. Production migration is explicitly out of scope.
- Maximum replay chain in this checkpoint: 128 entries. No fallback to an unverified base or deletion of local records.

## Synthetic durable relay
`wrangler.delta-dev.jsonc` defines a separate, loopback-only Worker with no public routes or binding to the live snapshot service. Explicit synthetic flag, loopback origin, and separate scoped test token hashes are required. Each scope uses an independent SQLite Durable Object.
- GET head, GET one revision, PUT initial anchor, PUT append. Writes use transactional expected-revision CAS; an exact retry of the last accepted ciphertext is idempotent. No overwrite or automatic history deletion.
- Maximum 1 MiB per PUT, one anchor plus 128 changes, 16 MiB ledger. Reaching the cap stops ordinary writes; explicit privileged compaction is available if a complete anchor fits.
- Only the authenticated client can interpret or validate encrypted content. The server checks envelope shape, bounds, authorization and sequence.
- The real local workerd test uses two scoped devices, races writes, restarts the worker, fetches a contiguous chain and reconstructs the full snapshot with the client codec. This is not a production migration or a normal application sync option.

## Explicit compaction and test client
`TEACHAPP_DELTA_COMPACT_HASHES` is an optional JSON object of separate per-area SHA-256 token hashes (must not equal ordinary access hashes). A compactor token cannot read or append, and an ordinary token cannot compact. The synthetic client uses both credentials only in memory and accepts HTTP loopback endpoints only.

The client reconstructs the remote state (not dirty local data), verifies the workspace, each revision, relationships and any retained local checkpoint, then encrypts a complete anchor at the next revision. Explicit confirmation and expected head revision are required. The Worker atomically inserts the anchor and removes superseded revisions using CAS; concurrent append and compaction cannot both succeed. Old revision requests return 410 and bounded readers restart from the new anchor. An exact retry is accepted while that anchor is the latest revision. After compaction, a fresh device reads the new anchor plus later deltas; an offline device with an older checkpoint keeps its own base and must reconcile explicitly. A checkpoint older than the retained anchor cannot independently verify the removed chain, and is marked as such. No local records are written by the LAB helpers.

This is a **trusted-client** operation: the opaque server cannot prove that a privileged writer's ciphertext contains the same state. Keep a verified encrypted backup before compaction; the prototype does not provide an immutable historical audit or Byzantine protection. No automatic compaction or normal sync integration, no chunked anchors above 1 MiB, no production deployment.

## Existing sync pipeline (synthetic integration)
`deltaLabSyncAdapter` requires explicit synthetic opt-in, injected data access and a loopback server. It implements the existing get/put interface: normal `prepareSync`, `previewSync` and `executeSync` retain scoped checkpoints and conflict/relationship validation. The full envelope returned to the existing pipeline is assembled and encrypted locally, never transmitted as an update. An initial anchor is sent once, later writes contain only changed records, and pulls use `reuseRemote:true` to avoid unnecessary revisions. A verified checkpoint checks the matching authenticated server entry and downloads only its tail. A compacted-away checkpoint requires explicit review opt-in before the existing three-way merge; it is not silently accepted.

The real workerd harness exercises two independent synthetic IndexedDB databases, edits to different records, a conflict with explicit resolution, and recovery after compaction. No ordinary UI or background auto-sync is connected to this adapter. The current implementation does not yet optimize the local full-envelope encryption cost, rotate encryption keys, handle chunked large anchors, or authorize a production migration.

## Multipart anchors (5.2 development)

The isolated LAB can now transfer an oversized initial or compacted anchor as a bounded sequence of 512 KiB base64 ciphertext segments (up to 30 parts, 15 MiB ciphertext, approximately 11.25 MiB plaintext before overhead). Each HTTP request remains below 1 MiB. This is **not** chunked deltas, production rollout or a change in the ordinary TAP1/TAC1 protocol.

The manifest describes the original envelope header, expected revision, operation kind, exact part lengths and SHA-256 hashes. Its normalized digest is the deterministic upload ID. The original AES-GCM ciphertext is reconstructed and decrypted by the existing client; the hashes are not a substitute for authenticated encryption or workspace/revision/relationship validation. One staging slot per scope, 10 minute expiry (cleaned on later writes), bounded storage. No staged part is readable as a published revision. Explicit commit verifies all parts, CAS, capacity and atomically creates the anchor and its part rows; compaction also removes superseded revisions and part rows. The ordinary and compact credentials remain separate. Exact retry at the current head and resuming identical ciphertext are supported; a different upload cannot replace active staging. Failed or expired staging must be retried from the current head. A concurrent ordinary append may make a staged compaction stale; it must not replace the newer revision. Old part requests return 410. The privileged-client trust boundary remains; retain a verified backup.

The lab still encrypts/decrypts an entire anchor in memory, caps each delta at 1 MiB and ledger at 16 MiB, and does not solve key rotation, remote revocation of old ciphertext, arbitrary large databases or server-side denial of service by a credentialed writer. No production Worker deployment.

## Atomic key rotation (synthetic LAB only)
A separate per-contour rotation token hash (TEACHAPP_DELTA_ROTATE_HASHES) authorizes only multipart rotation. The owner client reads and validates the current remote snapshot with the old password, generates a random 256-bit password and independent random device/compactor tokens, encrypts the unchanged remote snapshot at revision +1, and produces a separate encrypted recovery file. The caller must explicitly confirm a saved and verified recovery file before commit. A CAS checks the old revision and the client checks the remote digest. The staged manifest binds the replacement token hashes; the Durable Object atomically replaces the anchor, removes prior history, increments keyEpoch and replaces the ordinary and compactor allowlists. All requests are authenticated against the current persisted allowlist in the object; asynchronous writes recheck authorization inside the transaction. Old configured ordinary/compactor hashes are not restored on restart. Reuse of retired or statically configured hashes is rejected within the contour; independent generated random tokens prevent accidental cross-contour reuse. Rotation privilege stays separate and must be protected. A lost acknowledgement can be resolved from the recovery file by reading the exact new anchor with its new token. No private keys or plaintext are sent to the relay. A malicious privileged writer can still corrupt opaque ciphertext; a verified backup remains essential. Past copies are not erased from devices or provider backups. Existing local checkpoints encrypted with the old password require explicit rebind/merge; not yet automated. No production rollout.

### Offline device re-enrolment (synthetic)
After a successful rotation the owner may generate a separate encrypted device file for one ordinary token and the new encryption password. It includes the endpoint, contour, workspace, exact rotation anchor revision, digest and envelope hash, never the compaction/rotation tokens or other device tokens. A device must decrypt its old local checkpoint with the old password and verify the retained rotation anchor with the new token/password. A read-only preview reports counts and conflicts. Rebinding requires explicit confirmation of the two reviewed revisions and explicit acceptance of a historical base if its revision predates the rotation's predecessor. It re-encrypts only the previous local ancestor with the new password and clears the stale success timestamp; it does not alter business records, upload, or advance the checkpoint. Ordinary explicit three-way merge under the new credentials then requires acceptCompactedHistory and all conflict choices. If the rotation anchor is no longer retained, the file does not auto-rebind. A historical local base is authenticated by the old password, but its deleted server history cannot be independently proven; retain verified backups and review carefully. No UI or production integration.

## Локальный центр синхронизации (delta-dev)
Открывать только на локальном HTTP localhost / 127.0.0.1, не через опубликованный сайт. Настроить отдельный Worker с флагом TEACHAPP_DELTA_SYNTHETIC=true, разрешённым origin страницы и тестовыми хешами ключей. Интерфейс проверяет healthz и показывает только метаданные контура, объём, число ревизий, эпоху ключей; проверка расшифрованного снимка показывает только количество записей. В пустом контуре можно явно создать фиксированный синтетический набор. Все ключи и файлы только в памяти текущей вкладки; ни IndexedDB, ни localStorage, ни sessionStorage не открываются для данных. Рабочий интерфейс и профиль TAP1/TAC1 не изменены. Компактизация требует отдельного ключа и подтверждения. Ротация требует отдельного пароля, скачивания и повторного выбора точного файла владельца с успешной расшифровкой и подтверждения отзыва; при потере ответа сохраняйте файл. После подтверждения можно скачать отдельный файл каждого устройства, затем войти с ним и проверить новый снимок или восстановить кабинет владельца из его файла. Устройство не получает ключ компактизации или ротации. Кабинет не меняет локальные контрольные точки обычного приложения: rebind и явное слияние проверяются в отдельном синтетическом harness. Не вводите реальные секреты даже в лаборатории.

## Репетиция переноса со старого сервера (только LAB)
Функции prepareDeltaMigration, openDeltaMigration, inspectDeltaMigrationDevice и commitDeltaMigration работают только с двумя разными локальными HTTP origin и явным synthetic:true. Источник — существующий v1/v2 relay, только GET. Назначение — пустой Delta LAB. Три разных пароля (старый, новый и файла), два независимых токена. Новый workspace ID и ревизия 1 не переиспользуют старую последовательность. Проверяются связи, обе расшифрованные версии и SHA-256 снимка; защищённый файл содержит исходный и новый шифротекст без токенов или паролей. Пустой, несвежий или изменённый локальный контур диагностируется отдельно, без записи в IndexedDB.

Перед копированием нужно сохранить и проверить файл, остановить запись на всех устройствах источника, явно подтвердить операцию. Точная ревизия и исходный шифротекст сверяются до копирования, после — повторно; назначение читается и проверяется независимо. При изменении источника до копирования операция не пишет в LAB. При поздней записи остаётся отдельная проверенная копия, статус source-changed, переключение запрещено. Не перезаписывать непустое назначение; допускается только точный повтор текущего первоначального снимка. Client-side подтверждение **не является серверной блокировкой**. Даже verified-copy не разрешает автоматически менять профиль или контрольную точку устройства. Нужны серверное замораживание/lease, подтверждение всех локальных копий, раздельная приёмка и план отката. Реальный тест использует временный legacy relay и новый workerd с синтетическими записями; production и обычный TAP1/TAC1 не затрагиваются.

## RC4 — отдельный HTTPS v3 candidate

`wrangler.delta-candidate.jsonc` — отдельный Worker identity, без public/preview routes и без vars/secrets. Только explicit `TEACHAPP_DELTA_CANDIDATE=true`, точный HTTPS origin приложения и отдельный HTTPS origin `TEACHAPP_DELTA_ENDPOINT`; LAB и candidate взаимоисключающие. v3 использует `/v3/delta/`, а не `/v1/snapshot/` или LAB `/v1/delta/`. Head требует `protocolVersion:3` до записи, без fallback. Клиентский v3 adapter требует explicit confirmation; контрольная точка маркируется `delta-v3`; старые checkpoint и LAB binding не принимаются без отдельного переноса. Не подключать рабочий сервер: source fence, устройство, UI и подтверждение отката требуют продолжения. CI только синтетические данные, dry-run без deploy.

Штатный экран синхронизации теперь предлагает явный Delta v3 только в защищённом тестовом v11 профиле. Новый контур и обычный sync executor используют общий CAS, помеченные checkpoint/status, no-op pull, отказ от v1/v2 и запрет удаления привязки. Коды старого протокола не используются. Действующие v1/v2 устройства ещё не переключаются.
