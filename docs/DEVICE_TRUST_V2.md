# TeachApp — доверенные устройства, проект протокола v2

**Статус: изолированная серверная реализация для тестирования, не развёрнута.** Рабочий TAP1/TAC1 и клиентское приложение не изменены. Полный этап 1.2 не завершён.

## Ограничение v1

Личный код TAP1 содержит один общий 256-битный seed. Из него на каждом устройстве выводятся ключи доступа и пароли шифрования school/coach. TAC1 выдаёт этот же код получателю. Worker проверяет хеши токенов из конфигурации. Удаление локальной записи или имени устройства не может лишить старого обладателя TAP1 доступа: он заново выведет тот же токен. Смена одного лишь имени/идентификатора устройства не помогает.

## Целевая модель

- Отдельный административный ключ владельца, не выводимый из TAP1 и не передаваемый помощникам. Для первоначального включения владелец задаёт его хеш через защищённую конфигурацию Worker; не публиковать в Git и не хранить в открытом профиле браузера без явного решения.
- Случайный уникальный ключ доступа для каждого устройства, хеш на сервере; идентификатор, нейтральное имя, время создания/последней подтверждённой операции, разрешённые контуры, состояние отзыва.
- Ключ шифрования снимка и серверный токен авторизации разделены. Сервер не получает открытые данные, пароль расшифрования или TAP1. Временное приглашение содержит зашифрованный пакет с индивидуальным ключом/ключом шифрования; одноразовое погашение атомарно, TTL 10 минут, ограничения размера и частоты.
- Каждый GET/PUT и операции управления проходят серверную проверку действующего устройства. Проверка отзыва и изменение ревизии должны иметь согласованную транзакционную границу: нельзя принять ранее авторизованный PUT после подтверждённого отзыва. Админ-операции проверяют отдельный ключ; обычный токен не может выдавать или отзывать другие устройства.
- Не выдавать список ключей, хешей, личные данные учеников, содержимое пакетов. UI отображает только безопасные метаданные устройства. QR — альтернативное представление одноразового приглашения, а не мастер-ключа.

## Миграция без потери данных

1. Создать защищённую резервную копию; синтетическая тестовая среда и отдельные учётные данные.
2. Реализовать реестр и v2 в отдельной ветке, не меняя production. Проверить тесты конкурентных GET/PUT, отзыва, приглашения, повторного погашения, отказа при неверном токене, лимитов, несовместимых клиентов.
3. Получить явное разрешение владельца на изменение Worker и его конфигурации; включить v2 рядом с v1, выдать индивидуальные ключи только доверенным устройствам. Сохранять исходные ревизии/снимки. Проверить оба контура.
4. Лишь после подтверждения всех нужных устройств отключить v1-токены на сервере. Пока v1 доступен, отзыв нельзя считать полным. При компрометации TAP1 отдельно ротировать ключ шифрования согласованным протоколом; ранее скачанные копии невозможно отозвать. Не перешифровывать снимок наугад и не очищать базу.
5. Откат до отключения v1 возможен без изменения данных; после отзыва нельзя включать старый скомпрометированный токен как штатный откат. Восстановление — по защищённой копии и процедуре владельца.

## Приёмка

- Два устройства с разными ключами: оба синхронизируют только назначенные контуры.
- После отзыва A его GET и PUT возвращают отказ, включая конкурентный запрос; B продолжает работу. Старый TAP1 не даёт доступа после завершённой миграции.
- Временный код истекает и погашается один раз даже при конкуренции; ошибки не раскрывают секреты.
- Смена ключа не сбрасывает ревизии и не уничтожает данные; старый ключ больше не принимается.
- Потеря телефона, восстановление владельца и перенос существующей базы проверяются на синтетических данных.
- UI не имитирует отзыв и не сообщает о готовности, пока production не переведён и не проверен с разрешения владельца.

## Реализация серверного ядра (изолированная ветка)

- Опциональный `TEACHAPP_SYNC_ADMIN_HASH` включает v2; отсутствие настройки оставляет v1 без изменений. Административный ключ не принимается как ключ снимка; legacy-токены нельзя зарегистрировать как индивидуальные при включённом v1.
- `GET /v2/devices/{area}` — список безопасных метаданных; `POST /v2/devices/{area}` — создание с полями id, name, tokenHash; `POST /v2/devices/{area}/revoke` — отзыв по id. Все требуют административный bearer. Хеши не возвращаются. Список ограничен 128 записями на контур, включая отозванные; повторное использование id/ключа запрещено.
- `GET/PUT /v2/snapshot/{area}` — индивидуальный bearer; авторизация и CAS в одном SQLite Durable Object. Проверка производится повторно после чтения тела, в транзакции записи. Отозванное устройство не может записать новую ревизию после подтверждённого отзыва. Ревизии v1 и v2 общие, миграция не копирует и не сбрасывает снимок. Последний доступ на чтение сохраняется с точностью до пяти минут для экономии записей, на успешной записи — сразу.
- При тестовом отключении всех legacy-хешей v2 продолжает работать с тем же снимком; ни один старый TAP1 не должен авторизоваться. Для production требуется отдельное разрешение и безопасное подключение клиентов. Индивидуальные токены должны быть случайными и отличаться от административного/legacy ключей.
- Не реализованы пользовательский интерфейс и хранение профиля, QR, восстановление владельца и ротация шифрования. Серверную ветку не объединять и не развёртывать до завершения этих задач и приёмки.

## Индивидуальное приглашение v2

`TAD2` — новый тип одноразового кода; v1 TAC1 и v2 TAD2 используют разные Durable Objects и domain-separated доказательства. Клиентский модуль `js/device-trust.js` создаёт случайные отдельные токены контуров и регистрирует только их хеши. В приглашение попадают ключи шифрования снимков и индивидуальные токены, а не исходный TAP1. Профиль шифруется AES-GCM с одноразовым секретом, TTL 10 минут. Повторное погашение запрещено сервером. Список/отзыв требуют административного ключа; клиент не сохраняет его автоматически. При частичной ошибке создания клиент пытается отозвать все затронутые контуры, а при невозможности выводит ID для ручного отзыва. Отзыв одного контура не означает отзыва остальных. При замене ключа сначала выдать новый профиль и подтвердить его работу, затем отозвать старый. Повторное использование старых id/хешей запрещено. Смена ключа авторизации не перешифровывает историю и не сбрасывает ревизии.

Модуль пока не подключён к рабочему UI и автоматическому обмену. Он не предназначен для production без безопасного интерфейса, отдельного разрешения и проверки миграции. Тесты используют временную локальную workerd-среду.
