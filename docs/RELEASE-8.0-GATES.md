## Автоматическая проверка

Проверить точный SHA этого PR: npm test, npm run validate, Chromium, WebKit (реальный upgrade), синтетические Cloudflare/Delta/Platform/Firebase, отсутствие производственных deploy. Никаких личных данных в тестах.

## Устройства и миграции

Перед установкой на рабочие устройства сохранить зашифрованные независимые копии. Проверить открытие офлайн, журнал, синхронизацию, LIVE, импорт/экспорт, уведомления и восстановление на PC/iPhone. Не активировать LAB на рабочих данных. Отдельно проверить конфигурацию и секреты каждого сервера, staged migration и откат; никаких изменений Firebase/Worker без проверенного плана. Старые импортированные .ics с UID, содержащим дату, могут потребовать удаления дубля при повторном импорте. События из экспортированного календаря не обновляются автоматически.


## Отчёт доказательств перед финальным review 8.0

Для каждого нового кандидата создать локальный пустой отчёт (не коммитить рабочие акты):

```sh
SHA=$(git rev-parse HEAD)
node tools/release-readiness.mjs --template "$SHA" > release-evidence.json
node tools/release-readiness.mjs --check "$SHA" release-evidence.json
```

Для workflow указывать только ID успешного/неуспешного GitHub Actions run точного SHA; для физической/эксплуатационной проверки — только непрозрачный ID отдельного локального акта. Не записывать персональные данные, ссылки с токенами, ключи или снимки. Статусы pending/failed/passed; pending всегда без evidence. Код возврата 2 означает незакрытые проверки, 1 — неверный отчёт, 0 — все декларации заполнены для **ручного** review. Инструмент не обращается в GitHub, не проверяет акты, не заменяет независимое подтверждение, не меняет версию и не запускает deploy. После изменения SHA составить новый отчёт и повторно подтвердить применимость доказательств. Даже полностью зелёный CI не разрешает production cutover.

## Независимая сверка GitHub Actions

`node tools/release-ci-evidence.mjs SHA > release-evidence.json` создаёт новый отчёт по фиксированным ID шести workflow в Forz1k/teachapp. Использует только GET официального API, точный head_sha, push в roadmap/8.0-integration и тот же head repository. Проверяет последний run_number/attempt, не принимает старый success вместо незавершённого или failed запуска, не принимает PR merge-ref и неполный ответ. При API-ошибке не выдаёт отчёт; при необходимости можно задать GH_TOKEN с минимальными правами чтения, токен не выводится. Все 18 ручных условий остаются pending. Это сверка метаданных CI, не проверка качества тестов, физических актов или production; никакого deploy. Не перезаписывайте ранее заполненный отчёт без отдельной копии.

## Финальный контроль перед review

После заполнения локальных актов выполните `node tools/release-ci-evidence.mjs --verify SHA release-evidence.json`. Режим заново проверяет CI и что ветка интеграции имеет именно SHA до и после сбора. Он не доверяет старым CI-декларациям. `--refresh SHA FILE` выводит обновлённый JSON, сохраняя только ручные декларации того же SHA. Не направляйте вывод в исходный файл (shell очистит его до чтения). Используйте временный файл, проверяйте код возврата (0 — все декларации для ручного review, 2 — блокеры, 1 — ошибка/отчёт невалиден). Это точечная сверка, не блокировка ветки: перед merge/deploy снова проверить HEAD, CI, акты и план отката. Никаких автоматических публикаций.

Порядок и критерии каждого из 18 актов: [RELEASE-8.0-ACCEPTANCE.md](RELEASE-8.0-ACCEPTANCE.md).

## Статический пакет для review

Основной CI собирает `teachapp-static-review`: только явно перечисленные production-файлы из precache, sw.js и .nojekyll. Проверяет относительные зависимости модулей, HTML и манифеста, отказывается от symlink, пути за пределами allowlist или перезаписи существующего каталога. LAB, server, tools, тесты, конфиги и документация не входят. Это CI-артефакт, не Pages deployment: фактический способ публикации, настройки GitHub Pages и проверка сайта после deploy требуют отдельной приёмки. Для локальной сборки `node tools/build-static-release.mjs NEW_OUTPUT_DIRECTORY`.
