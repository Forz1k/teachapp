Проверить точный SHA этого PR: npm test, npm run validate, Chromium, WebKit (реальный upgrade), синтетические Cloudflare/Delta/Platform/Firebase, отсутствие производственных deploy. Никаких личных данных в тестах.

## Устройства и миграции

Перед установкой на рабочие устройства сохранить зашифрованные независимые копии. Проверить открытие офлайн, журнал, синхронизацию, LIVE, импорт/экспорт, уведомления и восстановление на PC/iPhone. ## Отчёт доказательств перед финальным review 8.0

Для каждого нового кандидата создать локальный пустой отчёт (не коммитить рабочие акты):

```sh
SHA=$(git rev-parse HEAD)
node tools/release-readiness.mjs --template "$SHA" > release-evidence.json
node tools/release-readiness.mjs --check "$SHA" release-evidence.json
```

Для workflow указывать только ID успешного/неуспешного GitHub Actions run точного SHA; для физической/эксплуатационной проверки — только непрозрачный ID отдельного локального акта. Не записывать персональные данные, ссылки с токенами, ключи или снимки. Статусы pending/failed/passed; pending всегда без evidence. Код возврата 2 означает незакрытые проверки, 1 — неверный отчёт, 0 — все декларации заполнены для **ручного** review. Инструмент не обращается в GitHub, не проверяет акты, не заменяет независимое подтверждение, не меняет версию и не запускает deploy. После изменения SHA составить новый отчёт и повторно подтвердить применимость доказательств. Даже полностью зелёный CI не разрешает production cutover.

## Независимая сверка GitHub Actions

`node tools/release-ci-evidence.mjs SHA > release-evidence.json` создаёт новый отчёт по фиксированным ID шести workflow в Forz1k/teachapp. Использует только GET официального API, точный head_sha, push в roadmap/8.0-integration и тот же head repository. Проверяет последний run_number/attempt, не принимает старый success вместо незавершённого или failed запуска, не принимает PR merge-ref и неполный ответ. При API-ошибке не выдаёт отчёт; при необходимости можно задать GH_TOKEN с минимальными правами чтения, токен не выводится. Все 18 ручных условий остаются pending. Это сверка метаданных CI, не проверка качества тестов, физических актов или production; никакого deploy. Не перезаписывайте ранее заполненный отчёт без отдельной копии.

## Финальный контроль перед review

После заполнения локальных актов выполните `node tools/release-ci-evidence.mjs --verify SHA release-evidence.json`. Режим заново проверяет CI и что ветка интеграции имеет именно SHA до и после сбора. Он не доверяет старым CI-декларациям. `--refresh SHA FILE` выводит обновлённый JSON, сохраняя только ручные декларации того же SHA. Не направляйте вывод в исходный файл (shell очистит его до чтения). Используйте временный файл, проверяйте код возврата (0 — все декларации для ручного review, 2 — блокеры, 1 — ошибка/отчёт невалиден). Это точечная сверка, не блокировка ветки: перед merge/deploy снова проверить HEAD, CI, акты и план отката. Никаких автоматических публикаций.

Порядок и критерии каждого из 18 актов: [RELEASE-8.0-ACCEPTANCE.md](RELEASE-8.0-ACCEPTANCE.md).

## RC7 — миграции, совместимость и восстановление

Кандидат 8.0.0-rc.7. Стабильный исходник 6.0.7 закреплён по SHA `1017f187a3cc8c26b46e4936f9c60773b4512783`. Перенос новых LIVE-событий и шаблонов сохраняет прежние документы; WebKit репетирует фактическое обновление и обратное обновление v10, включая последующие записи и независимое восстановление. Нельзя возвращать старую версию поверх уже активированного v11/Delta v3. RC6 интегрирован; RC7 переносит изменения стабильной 6.0.7 и её историю в отдельной ветке, без изменений main. Перед интеграцией обязателен полный CI.

1. **Локальное хранилище.** Перед v11 открыть сохранённый файл через отдельную кнопку проверки копии. Аутентификация checkpoint обязательна; сверка источника выполняется повторно непосредственно при атомарной записи. Не запускать на рабочем профиле до приёмки. После активации новые записи защищаются актуальной независимой копией; восстановление — только в отдельный пустой профиль, с новыми независимыми паролями. Не удалять базу и не откатывать бинарник поверх v11.
2. **Delta.** Зафиксировать точную ревизию источника каждого контура, проверить копию и серверный fence; перенести в изолированное назначение, проверить привязки v11 и новую независимую копию. До активации доступны signed seal/rollback и возврат только после проверки всех устройств. После активации возврат без согласования новых данных запрещён. Проверка в local workerd не выдаёт разрешение на production.
3. **Firebase.** В отдельном контуре с candidate rules заморозить архив и медиа. Сохранить и повторно выбрать единую публичную JSON-копию с обоими архивами и медиа. Подтвердить полное совпадение, выполнить ограниченные create-only пакеты; перед активацией повторная сверка поколения и медиа. Отмена заморозки доступна до V3, после активации обратного переключения нет. Не развертывать правила на production без отдельной приёмки.
4. **Приёмка.** После слияния RC6 и RC7 повторить все exact-head workflow на интеграционной ветке, проверить артефакты, все 18 ручных актов и отдельные эксплуатационные миграции. Зелёный PR не является готовностью 8.0 stable. OBS исключён.

Владелец сообщил о резервной копии и разрешил публикацию кандидата. Обычная PWA сохраняет IndexedDB v10 и текущий обмен v1/v2, а новые операции v11/Delta v3/Firebase V3 доступны только на loopback-стенде. Это клиентское ограничение, не серверная авторизация. Уже существующий v11 профиль не удаляется. Правила Firebase, ключи, отдельные Worker и HTTPS Platform не переключаются. Отдельный кодовый backup main 6.0.7 сохранён. Физическая приёмка и независимые проверки 18 актов всё ещё обязательны перед stable 8.0.0. Не очищать рабочую базу; откат только на проверенном v10 пути с сохранением актуальной копии. Публикация Pages предварительной PWA не означает production cutover серверов.

Только GET к фиксированному публичному origin; никакого доступа к данным. Несовпадение или ошибка сети — красный CI, а не подтверждение публикации.
