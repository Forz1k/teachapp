# TeachApp 8.0 RC8 — операционный runbook

**Кандидат, не production.** Проверки CI не заменяют физические испытания, независимый аудит или согласие владельца. Никаких рабочих персональных данных, секретов или копий в Git, CI, скриншотах либо публичных артефактах. Main сохраняет стабильную 6.0.7. OBS исключён.

## 1. Зафиксировать пакет для приёмки

1. Заморозить точный SHA `roadmap/8.0-integration`, проверить открытый draft #116 и актуальный main. При изменении head или base остановить приёмку и пересогласовать пакет.
2. Снять read-only снимок GitHub: `node tools/release-candidate-review.mjs SHA > candidate-review.json`. Код 0 означает только наличие актуальных 12 push/PR проверок и трёх артефактов. При ошибке не использовать старый снимок вместо нового. Если нужен GH_TOKEN — только в локальном окружении, не в файле или аргументах.
3. Скачать три ZIP из одного точного основного push-run, указанного в снимке. Не использовать PR merge-ref, случайные архивы из Releases или распакованную папку без проверки.
4. С Python 3.10+ выполнить:
   ```
   python tools/release-artifacts.py SHA candidate-review.json teachapp-static-review.zip teachapp-static-manifest.zip teachapp-ui-smoke.zip
   ```
   Проверяются размер и SHA-256 всех трёх ZIP, архив манифеста, полный список и байты статического пакета, версия SW/app, совпадение precache и безопасные пути. UI-архив проверяется по digest и структуре, а не по содержанию скриншотов. Не извлекать потенциально недоверенный ZIP до проверки. Снимок локален, не является подписью; его происхождение и свежесть подтверждает оператор через GitHub.
5. После проверки распаковать только статический пакет в новую пустую директорию/изолированный HTTPS origin. Проверить через `node tools/release-package-integrity.mjs --verify PACKAGE SHA MANIFEST`, где MANIFEST извлечён из проверенного отдельного ZIP и находится вне PACKAGE. Не копировать поверх рабочего сайта. Архивы GitHub истекают; при отсутствии точных артефактов не заменять их локальной пересборкой.

## 2. Безопасность и операционная готовность Platform

- Отдельные HTTPS origin UI/API, route-free candidate Wrangler, отдельные DO и EDGE_LIMIT; не связывать LAB, production и личную синхронизацию. Проверить реальные deployment IDs, DNS, TLS, CORS, запрет direct routes и namespace ID. Не использовать секреты в shell history.
- Утвердить IdP, согласовать выдачу коротких RS256 access-токенов с точными issuer/audience/client_id и новым jti. Один успешный exchange на workspace: при 401 или неопределённом результате получить новый assertion, не повторять старый. В RC8 сохраняются только digest и expiry успешных обменов (до 4096 в workspace, удаление истёкших при следующем обмене); возможна исчерпаемая квота, не глобальная защита между workspace.
- При смене одобренного signing pin или operator identity старые opaque bearer не принимаются новой конфигурацией. Убедиться, что старые версии Worker не обслуживают запросы; при замене оператора сначала проверить независимый recovery. Новый токен требует новой аутентификации. Членство и данные сохраняются, согласие на Push не отменяется автоматически. При инциденте отдельно отключить доставку и отозвать членства/сессии. Старые RC6/RC7 candidate bearer не содержат epoch и требуют повторного входа.
- Ключи backup, push storage, root и независимое восстановление хранить отдельно; не переиспользовать. При backup сверять источник, не восстанавливать в существующее пространство, после восстановления заново выдать доступы. При потере или компрометации backup key не удалять исходные записи; согласовать отдельный перенос.
- Push отключён до независимого review. Согласовать HTTPS allowlist провайдеров, VAPID, срок подписки, хранение ключей, мониторинг 401/403/410/429/503 и неизвестных ответов. Проверить отмену на сервере и устройстве; запрос, уже отправленный провайдеру, отозвать нельзя. Не писать endpoint, VAPID, bearer, содержимое уведомлений или персональные данные в журнал.

## 3. Матрица физической приёмки

Полные критерии и неизменяемые 18 ID — в [RELEASE-8.0-ACCEPTANCE.md](RELEASE-8.0-ACCEPTANCE.md). Для каждого акта зафиксировать отдельно точный SHA, версию, дату, ответственного, тип устройства/ОС/браузер (без идентификаторов), синтетические входы, ожидаемый и фактический результат, PASS/FAIL и стоп-условие. Скриншоты/логи с синтетикой и без секретов хранить вне репозитория. В JSON только уникальный opaque ID акта.

| Порядок | Группа | Обязательные ID | Не считать доказательством |
|---|---|---|---|
| A | Изолированные PC/iPhone | pc-offline-upgrade, iphone-offline-upgrade, journal-keyboard, documents-export | WebKit-эмуляция или скриншот без перезапуска |
| B | Тренер и экспорт | coach-live-video-skills, studio-export, device-performance | Только один сет или синтетические счётчики запросов |
| C | Резервирование | encrypted-backup-restore, storage-migration-rollback | Открытие копии без фактического отдельного восстановления |
| D | Серверные контуры | delta-production-migration, archive-media-production-migration | Local workerd/Firebase emulator |
| E | Platform и Push | platform-identity-authorization, platform-external-rate-limit-recovery, notification-background-device | Синтетический JWT или перехваченный POST |
| F | Независимое решение | independent-security-review, privacy-legal-operations, production-config-and-secrets-review, release-version-changelog | Автоматически заполненный отчёт или одобрение собственным CI |

### Рекомендуемый начальный бюджет производительности (согласовать до теста)

Синтетический набор: 24 класса × 30 учащихся, 36 уроков, 12 команд, 1200 матчей; отдельно архив 8000 матчей и 8000 тренировок. На каждом устройстве фиксировать 5 холодных и 20 тёплых открытий, редактирование оценки, ввод/отмену розыгрыша, восстановление LIVE после закрытия PWA, экспорт, пиковую память если браузер предоставляет метрику. Не измерять на реальных учениках. Начальные предложения: тёплое открытие основных экранов ≤ 2 с (p95), локальный ввод/отмена ≤ 500 мс (p95), холодное открытие ≤ 5 с; ни одной потери записи, зависания/принудительной перезагрузки или лишней отправки. Если аппарат/архив иной, согласовать бюджет до измерения; не подгонять его после сбоя. При недоступной метрике памяти фиксировать ограничение, не придумывать значение. Эти пороги не являются измеренным результатом.

## 4. Переходы и стоп-условия

- v10 → v11: проверить отдельную копию и контрольные точки; миграция только после проверки аварийного доступа. Старый клиент не открывает v11. Возврат 6.0.7 допустим только на неизменённой v10; для v11 не заменять JS старой версией.
- Delta: сверить оба контура, независимую копию, signed source fence и pending checkpoint; rollback только до активации. Firebase: совместный frozen bundle архивов и медиа, create-only перенос и повторная сверка до V3. При неполном совпадении остановиться.
- При потере записи, чужом доступе, ошибке подписи/ключа, неопределённой ревизии, превышении бюджета или нарушении consent прекратить переключение. Не удалять исходник, не перезаписывать сервер старой копией. Сохранить актуальное состояние в отдельной защищённой копии, согласовать сверку и повторить с новым SHA при изменениях кода.
- Создать пустой отчёт `node tools/release-readiness.mjs --template SHA > release-evidence.json`; заполнять только реально проверенными уникальными ID. `node tools/release-ci-evidence.mjs --verify SHA release-evidence.json` проверяет свежий push CI и декларации, но не читает акты. Не коммитить отчёт. После решения владельца и отдельного независимого review подготовить stable 8.0.0, повторить full CI и обновление на точном stable SHA; не переименовывать RC8 и не использовать его артефакты как stable без повторной проверки.

**Не закрыто этим runbook:** 18 ручных актов, выбор и реальная интеграция IdP, секреты и серверы, физические PC/iPhone, независимый security/privacy/legal review и production миграции.
